# Обновление модулей с проверкой зависимостей

В Module Node Picker расширена кнопка **Refresh Custom Nodes Info**. После установки
этой версии перезапустите ComfyUI: новые Python routes регистрируются при запуске.
ComfyUI должен работать в Conda-окружении `p313-torch214-cu132`.

## Проверка и статусы

Нажмите **Refresh Custom Nodes Info**: она проверяет upstream и зависимости,
и публикует каталог и прежние маркеры из данных того же прохода. Старый
backend Refresh и повторный запрос проверки списка ComfyUI-Manager не запускаются.
После завершения остаётся короткая плашка **«Найдено обновлений: X модулей»**
и кнопка **«Обновить модули (X)»** для проверенного набора. Если такого набора нет,
кнопка неактивна. Причины пропущенных обновлений выводятся в основной консоли ComfyUI.
Зелёная отметка ✅ перед успешно обновлённым модулем восстанавливается из истории
worker и сохраняется при Refresh, перезапуске и повторном открытии панели.
В карточке модуля с найденным обновлением показывается только кнопка
**«Обновить модуль»**. Для проверенного апдейта она активна; для не прошедшего
проверку — неактивна, причины доступны в консоли ComfyUI. У актуального модуля
кнопки нет. Diff requirements и подробная диагностика в карточках не показываются.
После индивидуального обновления остальные кандидаты остаются доступны, а число
на общей кнопке уменьшается. Можно обновить модули по очереди и затем один раз
перезапустить ComfyUI. В карточках обновлённых модулей строка Status показывает
красное **«Требуется перезагрузка»** до нового запуска сервера. При добавлении
зависимостей оставшиеся проверенные wheel reports сверяются с новым окружением;
посторонние изменения окружения требуют повторной проверки.

Модули проверяются максимум четырьмя параллельными задачами; счётчик показывает
число завершённых проверок. Результаты сортируются независимо от порядка завершения.
Requirements анализируются только у модулей с новым commit. Одинаковые наборы
requirements/constraints проверяются один раз в пределах запуска; исходный граф
окружения также вычисляется один раз. Совместимость общего набора по-прежнему
проверяется перед предложением массового апдейта. Кэш между запусками не используется.

Backend получает точный upstream commit через Git. Fetch добавляет Git-объекты,
но не изменяет рабочие файлы, HEAD и FETCH_HEAD; remote-tracking ref обновляется,
чтобы прежний каталог использовал тот же результат проверки. Нужны отдельный Git-репозиторий,
настроенный upstream и возможность fast-forward. Незарегистрированные файлы,
включая кэши, настройки и файлы установщика, не блокируют обновление, если
upstream не занимает их путь. Проверяются также ignored-файлы: они не должны
быть молча перезаписаны Git. При конфликте отчёт указывает конкретный путь.

Отслеживаемые Python-кэши и отличия только CRLF/LF не считаются ручными правками
кода. Перед фактическим обновлением worker сохраняет их копии в
`.alexz-updates/<plan_id>/local-files/<module>/`. Для некорректных upstream-правил
переносов строк используется временное правило Git `info/attributes`; исходный
файл правил восстанавливается после операции, `.gitattributes` не меняется.
Кэши, которых upstream не касается, сохраняются. Реальные изменения содержимого
отслеживаемых файлов, Git index и незавершённый merge по-прежнему блокируют
апдейт с конкретной причиной. Это защита от неожиданного состояния, а не
утверждение, что пользователь вручную изменял модуль. Автоматический stash,
удаление незарегистрированных файлов и принудительный reset не выполняются.

Сравниваются requirements текущего и целевого commit, включая локальные вложенные
`-r`/`-c`. При изменённых requirements сначала выполняется dry-run. Изменения
версии, описания и прочих метаданных `pyproject.toml` не блокируют его.
После успешного dry-run изменения `install.py`, `setup.py`, `setup.cfg` или
`build-system` требуют отдельной проверки: эти файлы автоматически не исполняются.
Install scripts никогда не запускаются. Если requirements (включая вложенные файлы)
не изменились, доступно обычное обновление только кода без pip, даже при изменении
packaging/install scripts. Такое обновление не исправляет прежние проблемы зависимостей.

При изменённых requirements backend выполняет `pip install --dry-run --report`,
даже если декларации уже удовлетворяются установленными пакетами, закрепляя **все
существующие версии** constraints-файлом. Разрешены только wheels из PyPI.
Используется `--no-deps`: дочерние зависимости читаются из wheel metadata и
проверяются до следующего прохода resolver. Dry-run не получает transitive
URL/VCS requirements и не запускает их build backend. Editable, внешние includes,
нестандартные параметры pip и исходные сборки требуют отдельной проверки.

Backend проверяет предполагаемый граф всего окружения, Python/platform markers
и запрошенные extras. Исходные metadata-конфликты выводятся отдельно от новых.

- **Конфликтов не обнаружено**: существующие версии сохраняются; допустимо
  добавление совместимых wheel-зависимостей.
- **С риском**: нужна замена защищённого пакета, изменился packaging/install
  script или найдены новые конфликты.
- **Проверка не завершена**: ошибка Git/сети, detached HEAD, отсутствующий upstream,
  неподдерживаемые декларации или недоступный wheel. Это не доказанный конфликт.
- **Заблокировано**: обнаружен конкретный конфликт пути, реальное отличие отслеживаемого файла, изменение Git index или незавершённый merge.
- **Актуально**: установлен целевой commit.

Результаты проверки и причины пропуска модулей выводятся в основной консоли ComfyUI.
Общая кнопка активна только после совместной проверки всего набора. При конфликте
набора кнопка неактивна; причина выводится в консоли ComfyUI.

Оценка не гарантирует работоспособность нового кода и не проверяет бинарный ABI
старых пакетов, системные библиотеки, CUDA kernels, импорты и поведение нод.

## Выполнение

1. Нажмите **«Обновить модули (X)»** рядом с короткой плашкой результата проверки.
   Для отдельного модуля нажмите **«Обновить модуль»** в его карточке.
   Подтверждение показывает выбранные модули и добавляемые пакеты.
2. Обновление выполняется сразу при работающем ComfyUI. Очередь заданий должна
   быть пустой. Не запускайте генерацию и не перезапускайте сервер до завершения.
   На время выполнения весь виджет блокируется: кнопки, выбор модулей, поля и вставка нод.
   Основная консоль ComfyUI показывает обновляемый модуль, вывод Git и ошибки;
   копия вывода сохраняется в `.alexz-updates/<plan_id>/worker.log`.
   В виджете остаётся только короткий статус. После завершения или ошибки управление возвращается.
3. Дождитесь сообщения **«Обновление завершено. Перезапустите ComfyUI»**.
   Сохраните workflow и перезапустите ComfyUI, например через ComfyUI-Manager.
   Новый Python-код и frontend-модули загрузятся после перезапуска; hot reload не выполняется.
4. Проверьте startup log и выполните [browser smoke](GUIDE_BROWSER_SMOKE.md).
   Диагностика сохраняется в `.alexz-updates/<plan_id>/status.json` и `worker.log`.

Отчёт проверки сохраняется локально и восстанавливается после перезапуска,
если его срок не истёк. Перед применением HEAD и окружение проверяются повторно.
После выполненного или ошибочного апдейта для следующей операции нужна новая проверка.
Старые задания с `waiting_for_shutdown` не начинают обновляться автоматически:
используйте **«Отменить ожидающее обновление»**, затем выполните новую проверку.
Отмена доступна даже при потерянном отчёте. Начавшееся обновление не прерывается
кнопкой отмены. Worker контролирует пустую очередь перед операциями и обнаруживает
перезапуск сервера, включая `os.execv` с сохранением PID. Это не блокирует поступление
новых workflow через другие вкладки или API: во время обновления ими пользоваться нельзя.

Worker повторно проверяет срок плана (час после анализа), HEAD, отсутствие
мешающих обновлению изменений и fingerprint окружения. Применяется зафиксированный commit
через fast-forward с отключёнными Git hooks. Новые upstream commits не
подхватываются автоматически. Перед добавлением пакетов создаётся backup через
`conda create --clone` в каталоге задания. При ошибке backup обновление не начинается.
Затем скачиваются wheels из pip report с проверкой SHA256; установка выполняется
без повторного resolver: `pip install --no-index --no-deps <проверенные wheels>`.

Проверяются сохранение старых версий, добавленные версии и новые metadata-конфликты.
При ошибке код возвращается на старый commit только если не появились новые правки.
pip не транзакционен: после частичной установки восстановите окружение из
`environment-backup`, указанного в сообщении. Резервный commit сохранён в
`refs/alexz-backups/<plan_id>` каждого обновлённого репозитория.

## Апдейт с риском

Рискованные/непроверенные модули не включаются в общий проверенный апдейт.
Причины пропуска доступны в консоли ComfyUI. Отдельные рискованные операции
через backend API требуют явного подтверждения и не предлагаются в карточках.

Принудительная замена конфликтующих пакетов рабочего окружения не реализована.
Такие обновления следует отдельно проверять в копии окружения. Backup перед
проверенными добавлениями не является проверкой рискованного апдейта в копии.

## API и ограничения

- Core ComfyUI не обновляется. Legacy update/install routes остаются info-only/advisory.
- `/alexz_tools/update_plan_{status,check,apply,cancel}` доступны loopback-клиенту
  с локальным Host и совпадающим Origin. POST требует JSON и `X-Alexz-Update: 1`.
- Worker поддерживает POSIX, исключает параллельные задания и отказывается
  выполнять план, если ComfyUI снова запущен на том же порту. Это дополнительная
  проверка, а не блокировка запуска сервера: соблюдайте порядок запуска выше.
- `.alexz-updates/` исключён из Git. Он содержит задания, статусы и backup,
  который может занимать значительное место.
- [update_planner_smoke.js](../tests/browser/update_planner_smoke.js) проверяет
  компактный UI, блокировку всего виджета и восстановление управления на подменённых API-ответах без реальных апдейтов. Это не заменяет проверку
  новых routes в настоящем ComfyUI после перезапуска.

Для проверки нового UI сначала выполните основной browser smoke в отдельной
тестовой вкладке по `GUIDE_BROWSER_SMOKE.md`, затем в той же вкладке вызовите
Playwright MCP `browser_run_code_unsafe` с `filename`:
`tests/browser/update_planner_smoke.js` (при необходимости абсолютный путь).
Ожидается `status: PASS` и десять проверок, включая последовательные индивидуальные
апдейты, уменьшение счётчика и красный статус перезагрузки. API проверки и апдейта
подменяются; чтение каталога и карточек разрешено, остальные операции изменения
ALEXZ backend блокируются. Native confirm временно
подменяется только в тестовой вкладке и восстанавливается после сценария.
После проверки закройте только тестовую вкладку.
