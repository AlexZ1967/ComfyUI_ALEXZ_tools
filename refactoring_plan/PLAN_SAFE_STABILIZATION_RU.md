# ComfyUI_ALEXZ_tools — План щадящей стабилизации и рефакторинга

Статус: draft / рабочий план исполнения
Дата: 2026-04-23
Трекер исполнения: [SAFE_STABILIZATION_EXECUTION_TRACKER_RU.md](SAFE_STABILIZATION_EXECUTION_TRACKER_RU.md)
Основание:
- текущая структура проекта после Phase 0-4 рефакторинга;
- локальный обзор кодовой базы;
- локальные проверки в `p313`;
- необходимость сохранить уже сделанное и не вносить регрессии.

## 1) Цель

Довести проект до более стабильного и предсказуемого состояния без big-bang переписывания:
- не ломать текущий рабочий функционал;
- восстановить совместимость там, где рефакторинг уже разорвал старые контракты;
- убрать import-time побочные эффекты, мешающие тестам и headless-сценариям;
- продолжать декомпозицию только после стабилизации базового контура.

## 2) Главный принцип

Сначала стабилизация контрактов, потом улучшение архитектуры.

Это означает:
- не трогать одновременно backend, frontend и node runtime без необходимости;
- не делать массовых переименований в одном шаге;
- после каждого маленького изменения запускать короткий релевантный набор проверок;
- полный `pytest` использовать как контрольный рубеж между фазами, а не как первый шаг каждой правки;
- не менять публичное поведение, если это не требуется для устранения явного дефекта.

## 3) Текущая базовая картина

Локально подтверждено:
- `conda run -n p313 python utils/docs_check.py` → OK
- `conda run -n p313 pytest -q tests/test_smoke_nodes.py -k seam_match` → OK
- `conda run -n p313 pytest -q tests/test_phase0_baseline.py tests/test_module_browser_api_contracts_golden.py` → OK
- `conda run -n p313 node --check web/widget_visibility_profiles.js` → OK

Локально выявлено:
- полный `conda run -n p313 pytest -q` сейчас падает массово;
- есть разрыв совместимости по import-поверхности `utils.module_browser`;
- часть нод тянет GPU/Comfy зависимости на уровне импорта модуля;
- из-за этого ломаются unit-тесты, smoke-тесты и headless-импорт пакета.

## 4) Что считаем инвариантами

Во время выполнения этого плана нельзя ломать:
- текущие HTTP route contracts `Module Node Picker`;
- существующие frontend import paths, если они уже используются runtime-ом;
- реестр нод и их display/type names;
- документацию и `docs_check`;
- уже проходящие contract/smoke тесты;
- поведение GPU-only нод в production, если GPU действительно нужен по смыслу.

Разрешено менять:
- внутренние импорты;
- точки инициализации;
- thin compatibility shims;
- организацию helper-модулей;
- testability-слой без изменения пользовательского поведения.

## 5) Стратегия исполнения

Работа идет маленькими фазами.

Правило фазы:
1. Делаем только один класс изменений.
2. Прогоняем только релевантные проверки.
3. Если фаза зеленая, фиксируем результат и только потом идем дальше.
4. Если фаза не зеленая, не расширяем scope, а дочищаем текущую проблему.

## 6) Порядок фаз

## Phase A — Freeze и минимальный safety baseline

Цель:
- зафиксировать безопасную стартовую точку перед правками.

Задачи:
- не менять поведение нод и API в этой фазе;
- сохранить список текущих проходящих проверок как обязательный baseline;
- описать в changelog/рабочих заметках, какие тесты уже зеленые, а какие красные;
- при необходимости добавить короткий smoke-набор команд в рабочий чеклист разработчика.

Критерий выхода:
- есть явный baseline-комплект проверок для каждой следующей фазы.

Обязательные проверки:
- `conda run -n p313 python utils/docs_check.py`
- `conda run -n p313 pytest -q tests/test_phase0_baseline.py tests/test_module_browser_api_contracts_golden.py`
- `conda run -n p313 pytest -q tests/test_smoke_nodes.py -k seam_match`

## Phase B — Восстановление import-совместимости `utils.module_browser`

Цель:
- вернуть старую import-поверхность без отката всей декомпозиции.

Почему это первая техническая фаза:
- сейчас многие unit-тесты падают не из-за логики, а из-за разрыва API уровня package imports;
- это самый дешевый способ убрать большую группу регрессий.

Задачи:
- проверить, какие исторические импорты ожидаются тестами и внутренним кодом;
- добавить compatibility shims на уровне `utils/module_browser/`;
- для модулей вроде `value_ops`, `release_ops`, `state_store`, `runtime_refresh_ops` вернуть стабильные import-path entrypoints;
- внутри shim-модулей делать только реэкспорт целевых функций из новых поддиректорий;
- не дублировать бизнес-логику между новым и старым путями.

Требования к реализации:
- старые imports должны снова работать;
- новый layout каталогов должен остаться основным;
- `__init__.py` и shim-модули должны быть максимально тонкими.

Критерий выхода:
- минимальный набор module-browser unit-тестов начинает проходить без правок их логики;
- import-поверхность стабилизирована.

Прицельные проверки:
- `conda run -n p313 pytest -q tests/test_module_browser_value_ops.py`
- `conda run -n p313 pytest -q tests/test_module_browser_release_ops.py`
- `conda run -n p313 pytest -q tests/test_module_browser_state_store.py`
- `conda run -n p313 pytest -q tests/test_module_browser_runtime_refresh_ops.py`

**Дополнительный шаг:** после выполнения целевых тестов выполнить агрегирующий набор, например:

```
conda run -n p313 pytest -q tests/test_module_browser_*.py -x
```

Это быстро выявит любые скрытые регрессии в старой import‑поверхности.

## Phase C — Устранение import-time GPU/Comfy side effects

Цель:
- сделать модули import-safe без ослабления runtime-требований к GPU.

Принцип:
- GPU-only допустимо как runtime requirement;
- GPU-only недопустимо как package import requirement.

Основные кандидаты:
- `nodes/video_inpaint.py`
- `nodes/image_prepare.py`
- при необходимости другие ноды, которые тянут `comfy.model_management` или CUDA-зависимую инициализацию на верхнем уровне.

Задачи:
- перенести тяжелые импорты в функции/методы или в lazy helper-обертки;
- отделить “модуль можно импортировать” от “ноду можно реально выполнить”;
- при отсутствии GPU выбрасывать понятную runtime-ошибку в момент использования ноды;
- не менять существующие алгоритмы обработки.

Важно:
- не подменять реальную GPU-логику фейковым CPU fallback, если такого поведения раньше не было;
- не снижать качество/производительность production-сценария ради тестов;
- изменять только момент инициализации зависимостей.

Критерий выхода:
- headless import нод работает;
- целевые smoke/unit тесты больше не падают на `No CUDA GPUs are available` во время импорта.

Прицельные проверки:
- `conda run -n p313 pytest -q tests/test_smoke_nodes.py -k video_inpaint`
- `conda run -n p313 pytest -q tests/test_smoke_nodes.py -k image_prepare`
- `conda run -n p313 pytest -q tests/test_smoke_nodes.py -k seam_match`

## Phase D — Локальная стабилизация node loader

Цель:
- сделать поведение загрузчика нод более предсказуемым при частичных ошибках.

Задачи:
- проанализировать текущий контракт `nodes/__init__.py`;
- сохранить tolerant loading, если он нужен для ComfyUI runtime;
- улучшить диагностичность `LOAD_RESULTS`;
- по возможности отделить “ожидаемая недоступность runtime-зависимости” от “реальная ошибка модуля”.

Чего не делать:
- не превращать loader в жесткий fail-fast без явного решения;
- не менять format mapping dictionaries.

Критерий выхода:
- поведение загрузчика становится прозрачнее;
- тесты и импорт пакета меньше зависят от наличия конкретной железной конфигурации.

Прицельные проверки:
- `conda run -n p313 pytest -q tests/test_smoke_nodes.py`
- `conda run -n p313 pytest -q tests/test_slice0_registry.py`

## Phase E — Закрытие backend helper regressions

Цель:
- после совместимости импортов и import-safety добить оставшиеся backend unit regressions.

Задачи:
- разбирать красные тесты по кластерам, а не по одному случайному файлу;
- идти в порядке:
  1. `core/value_ops`, `core/widget_mode_ops`
  2. `state/*`
  3. `git/*`, `release_ops`, `repo_bootstrap_ops`
  4. `jobs/*`, `update_ops`, `runtime_refresh_ops`
- если тест падает из-за контракта, сначала решить: это реальный баг или устаревший тест;
- если контракт уже принят и задокументирован, править код, а не тест, если нет сильной причины.

Отдельный caution:
- внимательно относиться к helper-ам, которые пишут в глобальную git-конфигурацию;
- любые side effect операции должны быть максимально явными и тестируемыми.

Критерий выхода:
- module-browser suite в основном зеленая;
- регрессии сведены к небольшому понятному хвосту, а не к массовому шуму.

Рекомендуемые проверки:
- `conda run -n p313 pytest -q tests/test_module_browser_*.py`

## Phase F — Контрольный полный прогон

Цель:
- проверить, что локальные точечные улучшения действительно стабилизировали весь репозиторий.

Задачи:
- запуск полного `pytest`;
- разбор остаточных падений по группам;
- отделение реальных багов от средозависимых ограничений;
- фиксация нового baseline.

Критерий выхода:
- либо полный `pytest` зеленый;
- либо остался короткий, явно описанный список known failures с понятными причинами и отдельным планом.

Проверки:
- `conda run -n p313 pytest -q`
- `conda run -n p313 python utils/docs_check.py`
- `conda run -n p313 node --check web/widget_visibility_profiles.js`

## 7) Тактика изменений внутри каждой фазы

Для каждого PR/коммита в рамках плана:
- менять как можно меньше файлов;
- не смешивать совместимость импортов и функциональные изменения алгоритмов;
- сначала добавлять shim/guard, потом при желании чистить внутренности;
- если приходится менять тесты, делать это только после явной фиксации причины;
- все новые helper-файлы делать тонкими и очевидными.

## 8) Что специально не делаем сейчас

Не делаем в этом плане:
- новую большую frontend-перестройку `Module Node Picker`;
- унификацию всех нод через общий base class;
- массовое переименование файлов под новый стиль;
- перенос всего на async/queue архитектуру;
- оптимизации ради красоты без тестового выигрыша;
- CPU fallback для GPU-heavy нод, если это меняет обещанное runtime-поведение.

## 9) Риски и как их снижать

Риск 1: случайно сломать уже рабочие route contracts
- Снижение: backend API-contract tests гонять после каждой backend-фазы.

Риск 2: восстановить старые импорты ценой дублирования логики
- Снижение: только shim/re-export, без копирования реализации.

Риск 3: “починить тесты” за счет размытия runtime-требований
- Снижение: переносить только момент проверки GPU, а не убирать само требование.

Риск 4: начать широкую чистку и потерять контроль над регрессиями
- Снижение: один класс изменений на фазу, узкий набор проверок, затем фиксация результата.

## 10) Определение готовности

План можно считать успешно выполненным, когда одновременно верны условия:
- старые import-path контракты `utils.module_browser` снова рабочие;
- import нод не требует наличия CUDA на этапе загрузки пакета;
- текущие green baseline-проверки не деградировали;
- полный `pytest` либо зеленый, либо оставшиеся падения локальны, понятны и явно оформлены;
- дальнейшие архитектурные улучшения можно делать уже не в режиме аварийной стабилизации.

## 11) Практический порядок исполнения

Рекомендуемый фактический порядок работы:
1. Phase A
2. Phase B
3. Phase C
4. Phase D
5. Phase E
6. Phase F

Если в процессе выяснится, что часть падений из Phase E на самом деле вызвана еще не закрытой import-time проблемой, возвращаемся в Phase C и не расширяем scope дальше.

## 12) Короткий рабочий чеклист перед каждым изменением

- Проверен scope: только одна цель на текущий шаг.
- Подобран минимальный набор тестов для этого шага.
- Не меняются одновременно публичные контракты и внутренняя архитектура.
- Команды запускаются через `conda run -n p313`.
- После локальной зеленой проверки фиксируется результат и только потом начинается следующий шаг.

## 13) Автоматизация и поддержка CI

**Baseline‑capture** – добавить скрипт `scripts/save_baseline.sh`, который сохраняет хеши проходящих тестов и список зелёных проверок в `baseline.json`. Использовать его в фазе A и перед каждым PR.

**CI‑интеграция** – в CI добавить отдельный job «stabilization‑baseline», который запускает набор тестов из фазы A и проверяет соответствие `baseline.json`. В шаблоне PR включить чек‑лист `baseline‑check passed`.

**Changelog‑автообновление** – скрипт `scripts/update_changelog.py` автоматически дополняет `CHANGELOG.md` после успешного завершения каждой фазы (записывает номер PR, дату, список исправленных тестов).

**Coverage** – в фазе E запускать `pytest --cov utils/module_browser` и требовать минимум 80 % покрытия новых/исправленных модулей.

**Линтер/Static analysis** – перед каждой фазой выполнять `ruff`/`flake8` (или аналог) для обнаружения новых import‑тайм side‑effects и циклических импортов.

**Rollback‑план** – в случае критической регрессии `git revert` последнего стабилизирующего PR; CI‑pipeline должен останавливать деплой, пока не будет выполнен откат.

**Post‑release мониторинг** – после слияния последнего PR запускать скрипт `scripts/post_release_check.sh`, который повторно выполняет полный `pytest` и проверяет, что baseline‑тесты остаются зелёными.

**Явные зависимости** – в `pyproject.toml` явно указать минимальные зависимости для `utils.module_browser`, чтобы `pip install -e .` не устанавливал GPU‑зависимые пакеты автоматически.

**Документация** – добавить в `README.md` секцию «Stabilization workflow», описывающую процесс baseline‑capture, CI‑чек‑лист и как откатывать изменения.
